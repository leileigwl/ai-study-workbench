# 数据库 MVCC 与 Write Skew — 提炼标准答案与模拟评分卡（AI 专用）

> **所属类型**：`interview`  
> 专供 AI 教练核对 `workbench.zh-CN.md` 与执行第 4 步脱稿模拟面试。请勿在做题前偷看。

---

### Q1.1 MVCC 如何让大查询和密集更新并发不阻塞？
- **标准答案要点（`3` 个）**：
  1. **多版本追加不原地覆盖**：写操作不覆盖原数据，而是追加带事务可见区间（`xmin`/`xmax` 或 Undo Log）的新版本。
  2. **一致性快照水位线**：事务启动时拿到当时活跃事务列表快照，只看“启动前已提交”的版本，忽略后续新提交。
  3. **读写锁彻底解耦**：读不加共享锁所以不挡写，写也只和改**同一行**的写互相排队。
- **漏点追问话术（绝不直接剧透）**：
  - *若漏掉第 2 点*：“事务 A 早上 10:00 开始跑一个慢查询；10:02 事务 B 把余额改掉并成功提交。不锁整张表的前提下，事务 A 凭什么还能稳稳读到 10:00 那一刻的旧余额？”

### Q1.2 为什么 `REPEATABLE READ` 依然会出现“零医生值班”的 Write Skew？
- **标准答案要点（`3` 个）**：
  1. **写集不相交（First-Committer-Wins 放行）**：快照隔离只冲突拦截“修改同一行”的并发写入；A 和 B 改的是各自不同的行，校验全放行。
  2. **基于同一份过时快照做判断**：两个事务检查 `count >= 2` 时都没看到对方还没提交的新修改。
  3. **跨行约束根治方案**：升级为 **`SERIALIZABLE`（SSI 谓词冲突检测）**，或者引入/锁住共同父记录（如对 `SHIFT` 班次主行做 `SELECT ... FOR UPDATE`）。
- **漏点追问话术**：
  - *若漏掉第 3 点*：“如果面试官告诉你：把整库隔离级别改成 `SERIALIZABLE` 后高峰期事务重试报错暴涨，要求你在保留 `REPEATABLE READ` 的前提下修掉这个漏洞，你改哪？”
